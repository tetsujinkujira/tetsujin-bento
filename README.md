## 更新と公開確認

### 編集先

| 変更する内容 | 編集するファイル | 編集箇所 |
|---|---|---|
| お知らせ | `public/data/site-config.json` | `news` の `title`・`date`・`category`・`body` |
| 日替わり | `public/data/site-config.json` | `daily` の年・月・曜日別メニュー・価格 |
| 通常メニュー・価格・トッピング | `public/data/site-config.json` | `menu.items` の該当品目・`toppings` |
| サイドメニュー | `public/data/site-config.json` | `menu.sideMenus` |
| 店舗情報・受付時間・配達案内 | `src/` の該当HTML | 複数ページに同じ情報がある場合は全箇所を確認 |
| 画像 | `public/images/` | JPGとWebPがある場合は両方を更新 |

更新データは `public/data/site-config.json` の1ファイルです。`news`・`daily`・`menu` に分かれています。日替わりの名称・価格は `daily` の値だけを使います。`dist/` は生成物なので直接編集しません。

旧JSON、ルートの `data/`・`assets/`、旧Decap管理画面は削除済みです。元ファイルはGit履歴とローカルバックアップで復元できます。公開ページ・URL・デザイン・画像は維持しています。店舗情報・配達エリア等のHTMLを今回データ化したわけではありません。

### フォームから更新する（Pages CMS）

お試し用ブランチは **`pages-cms-test`** です。Pages CMSでは必ずこのブランチを選んで保存してください。このブランチのpushではビルドとテストのみを実行し、本番公開はスキップします。`main`に保存すると本番公開が始まります。


リポジトリ直下の `.pages.yml` に、単一の「サイトを更新」フォームを定義しています。中は「お知らせ」「日替わりメニュー」「商品・価格」に分かれ、JSONの記号を編集する必要はありません。価格は数値、日付と月は選択式です。ID・画像情報・カテゴリ設定は保護しています。

接続前の準備状態です。次の初回設定はリポジトリ所有者が行います。

1. この変更をGitHubに反映し、[Pages CMS](https://app.pagescms.org/)にGitHubでログインします。
2. GitHub Appを `tetsujinkujira/tetsujin-bento` のみに許可します。
3. このリポジトリと対象ブランチを選び、「サイトを更新」を開きます。
4. 初回はテスト用ブランチで1項目を変更・保存し、変更が `site-config.json` だけに収まり、他の商品・画像情報・内部設定が欠落しないことを差分で確認します。
5. 検証後に戻すか `main` へ反映し、以下の公開確認を行います。接続後も保存と公開完了は別です。

商品・カテゴリの追加削除や画像の差し替えは担当者が行います。このフォームは既存品目の更新用です。商品説明は通常のテキスト入力で、看板メニューの改行は段落として表示します。

Pages CMSの設定ファイルはYAML互換のJSON形式で記述しています。フォームの実際の保存動作・スマートフォン操作は、アカウント接続後の初回検証が必要です。

### GitHubで編集する場合

1. `main` の最新ファイルを開き、上表の編集先を選びます。
2. 内容を書き換え、差分を確認して保存（Commit）します。お知らせの日付、日替わりの年・月、トッピング価格も確認します。
3. [公開処理の一覧](https://github.com/tetsujinkujira/tetsujin-bento/actions/workflows/deploy.yml)で、**自分が保存した変更の実行**を開きます。
4. `build-and-test` と `deploy` の両方が成功したことを確認します。保存だけでは公開完了ではありません。
5. [本番サイト](https://www.tetsujin-kujira.com/)と[メニューページ](https://www.tetsujin-kujira.com/menu.html)を再読み込みし、変更箇所を確認して完了です。

価格改定では通常価格・トッピング・トップページの価格を、日替わりでは月と全曜日を、お知らせではタイトル・日付・本文を確認します。PCとスマートフォンの両方で確認できると確実です。

### ローカルで編集する場合

1. 未コミットの変更を確認・保護し、GitHubの `main` の最新変更を取り込みます。取り込み時に競合したら解消してから編集します。
2. 上表のファイルを編集します。
3. `npm run validate:data` でJSONの構文・必須項目・価格・日付・画像を確認し、`npm run dev` で画面を確認します。
4. `npm test` でビルドと画面テストを確認します。
5. 変更をコミットして `main` にpushし、上記の公開処理・本番表示の確認まで実施します。

### 反映されない場合

- **実行中・待機中**：処理の完了を待ちます。所要時間だけで成功を判断しません。
- **Buildで失敗**：`JSON ERROR` のファイル名とエラー位置を確認します。末尾の余分なカンマ、カンマ忘れ、引用符を直して再保存します。
- **Run Playwright testsで失敗**：失敗したテストとログを確認します。通すためだけにテストを削除せず、表示やデータの問題を確認します。
- **deployで失敗**：公開処理のログを担当者に共有します。テスト成功だけでは公開完了になりません。
- **両方成功したのに古い**：対象の変更の実行か、編集先と本番URLが正しいかを確認し、再読み込みやプライベートウィンドウで比較します。配信キャッシュのため直後に差が出る場合があります。

失敗した場合、以前のサイトが表示されたままになることがあります。担当者には「変更ファイル・期待する内容・公開処理のURL・確認した本番URL」を共有してください。

保存済みの変更はブラウザーの「戻る」では取り消せません。取り消す場合は履歴から直前の内容を確認し、必要な箇所を戻して**新しいコミットとして保存**し、同じ公開確認を行います。
